# Trunk-Based Patterns

How this repository branches. Binding for humans and agents alike.
Machine-readable form: `trunk-based.json`. Enforced by a PreToolUse
guard, `.git/hooks/pre-push`, and remote branch protection.

> Generated by the `n1-general:trunk-based-development` skill. Re-run it to change any of
> this rather than editing both files by hand and letting them drift.

## The lines

| | Branch | Rules |
|---|---|---|
| **Trunk** | `windows-support` | The single integration line. Always green, always releasable. Never force-pushed, never deleted. |
| **Upstream mirror** | `main` | Not a deployment branch — strategy `trunk` has none. A pristine mirror of `restatedev/restate`, fast-forwarded from the `upstream` remote and nothing else. Declared foreign in `trunk-based.json`: never commit to it, never fork a leaf from it, never push it to `origin` as if it were ours. |
| **Leaves** | `leaf/<type>/<slug>` | Disposable. Max `24` hours. Max `3` open at once. Deleted on merge. |

`<type>` ∈ `feat` `fix` `refactor` `chore` `docs` `test` `perf`

## Verify

```
just verify
```

This runs **before** a leaf merges, not after. A leaf that has not passed it does
not reach `windows-support`. Failing verify is not a reason to merge with a note — fix it
or drop the leaf.

Review gate: **`self-on-green`**.

## The loop

```
 1. SYNC      git switch windows-support && git pull --ff-only
 2. BUDGET    at 3 leaves? land or delete one first
 3. SCOPE     one landable increment inside 24h; else split, or land it dark
 4. LEAF      git switch -c leaf/<type>/<slug>     (from windows-support, never from a leaf)
 5. WORK      small commits, in this repo, in place
 6. FRESHEN   git fetch && git rebase windows-support          (your leaf only — see Rebase)
 7. VERIFY    run the command above — it must pass
 8. GATE      releasable? incomplete work is flagged off, not held back
 9. REVIEW    self-on-green
10. LAND      git switch windows-support && git merge --no-ff leaf/... && git push
11. DELETE    git branch -d leaf/... && git push origin --delete leaf/...
12. CONFIRM   windows-support still green? judge the jobs, not the rollup — see Green
```

## Rebase

**Rebase your own leaf. Merge everything shared. Land by merge, always.**

Rebase copies commits rather than moving them: the originals are abandoned and
replacements take their place under new shas. Anyone who already fetched the
originals keeps them and has to re-merge by hand. A leaf is one workstation's
branch and nothing may be based on it, so it is yours to rewrite. `windows-support` and
`main` are not.

| Operation | |
|---|---|
| `git rebase windows-support` on your leaf | Fine — `windows-support` is read, not rewritten |
| `git rebase -i` on your leaf, pushed or not | Fine |
| `git push --force-with-lease` on your own leaf | Fine — this is how a rewrite gets published |
| `git push --force` (bare), anywhere | Banned |
| `git rebase` on `windows-support` or `main` | Banned — `git pull --ff-only` to catch up |
| Landing a leaf by fast-forward | Banned — `git merge --no-ff` |

Use the lease, not your judgement: `--force-with-lease` refuses when the remote
moved since your last fetch, which is the only evidence anyone else has the branch.
If it refuses, fetch and read what arrived. Do not force past it.

Do not rebase a leaf long enough to hide broken commits under a green tip — verify
only runs on the tip, and those commits poison a later `git bisect`. A leaf that
big is past `24`h anyway: land it or split it.

## Green

Step 12 asks whether `windows-support` is still green. Two rules for reading that, because
the poll loop is normally written wrong:

**Terminal is a negative test.** Do not list the statuses that mean *done* — that
set is open-ended, so a forgotten value either hangs the poll or ends it early.
List what is still **working** (queued, waiting, preparing, running, cancelling)
and treat everything else as finished.

**Judge the jobs, not the rollup.** A pipeline's summary status says what state the
pipeline is in, not whether your change passed. When the last stage is a manual
deploy gate, a fully green pipeline rolls up as that gate's status, so waiting for
a "success" rollup waits forever.

## Work that does not fit one leaf

Never hold the branch open. Three moves, in preference order:

1. **Split it.** Land the refactor first, the behaviour second.
2. **Land it dark.** Feature flag, default off: `add an `experimental_<name>: bool` to `CommonOptions` in `crates/types/src/config/common.rs`, default it `false` in the `Default` impl, and gate the new path on it — as `experimental_enable_vqueues` and `experimental_kafka_batch_ingestion` already do`. The code
   ships; the behaviour does not. Delete the flag once the path is permanent.
3. **Branch by abstraction.** For a replacement spanning many leaves: put an
   abstraction in front of the old implementation, build the new one behind the
   same shape, migrate callers one leaf at a time, delete the old one last.

## Releases — strategy `trunk`

Release from any green `windows-support` commit; there is no deployment branch and
no release branch. A bug is fixed forward, on a new leaf.

**What a push to `windows-support` triggers: nothing.** `.github/workflows/ci.yml`
runs on `pull_request`, `workflow_dispatch`, and pushes to `main` / `release-*`
only. This fork's trunk is not in that list, so no pipeline watches it. Two
consequences, and neither is optional:

1. **The local `just verify` is the whole gate.** On a repo with CI, step 7 is a
   pre-check and CI is the backstop. Here there is no backstop. A leaf that has
   not passed verify locally has not been checked by anything.
2. **Step 12 has nothing to poll.** Do not wait for a pipeline that will never
   start. To get CI on a change, open a pull request — the `pull_request`
   trigger fires regardless of base branch.

**Keeping `main` current.** `main` is a mirror, not a line of work:

```bash
git fetch upstream
git switch main && git merge --ff-only upstream/main   # fast-forward ONLY
git switch windows-support
```

If that `--ff-only` is ever refused, `main` has been written to by mistake —
reset it to `upstream/main` rather than merging.

**Carrying upstream into the port.** Upstream work reaches `windows-support` by
merging `main` into it on a leaf, verifying, and landing that leaf like any
other. Never the reverse: nothing this fork writes belongs on `main`.

**Sending work upstream.** A change that is not Windows-specific belongs in a PR
to `restatedev/restate`, cut from `main`, not from `windows-support`.

## Banned

| Banned | Instead |
|---|---|
| `git worktree add`, agent worktree isolation | Work in this repo, on a leaf |
| Cloning or copying this repo to a scratch dir | Same |
| Long-lived `develop` / `staging` / `integration` | `windows-support` is the integration point |
| Branching off a leaf; stacked leaves | Fork from `windows-support` only |
| A leaf older than `24`h | Split it, or land it dark |
| More than `3` leaves open | Land or delete first |
| `git push --force` to `windows-support` | Never, lease or no lease. Fix forward — rewriting trunk breaks every other checkout |
| Committing to `main`, or merging this fork's work into it | `main` mirrors upstream. Fast-forward it from `upstream` only |
| Opening a leaf from `main` | Fork from `windows-support`. A leaf off the mirror is based on code this fork has not ported |
| `git rebase` on `windows-support` or `main` | `git pull --ff-only` to catch up; rewrite your own work on a leaf |
| `git push --force` (bare) to your own leaf | `--force-with-lease` — it refuses if the remote moved |
| Landing a leaf by fast-forward, rebased or not | `git merge --no-ff` — no merge commit, no revert unit |
| Stashing work instead of landing it | Land a smaller increment |
| Merging on red verify to unblock | Fix it, or drop the leaf |
| Polling CI by listing the statuses that mean "done" | List what is still *working*; everything else is terminal |
| Reading the pipeline rollup to answer "did my change pass" | Judge the individual jobs — see Green |
| Code freezes, integration phases | Not needed when leaves are hours old |

## Targets

| Measure | Target |
|---|---|
| Active branches | ≤ `3` |
| Oldest leaf | < `24` hours |
| Merges to `windows-support` | ≥ 1 per developer per day |
| Code-freeze days | 0 |
| Time to review a leaf | minutes, not hours |

```bash
git for-each-ref --sort=committerdate \
  --format='%(committerdate:relative)  %(refname:short)' refs/heads
```

## If you are an AI agent

Read this file before touching code. You are on step 1 until you say otherwise;
name the step you are on as you go. If you skip a step, say which and why. When a
guard blocks you, the block message names the compliant alternative — take it.
Do not work around a guard, and do not reach for `--no-verify`.
